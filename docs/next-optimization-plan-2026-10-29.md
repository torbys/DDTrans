# DDTrans 后续优化计划

日期：2026-10-29。本文只列当前事实、尚未完成项和下一步验收；音频设置页不是未来阶段，已经在本轮第四步完成。

## 本轮已完成

1. 48 kHz、单声道真实混音：原声与 24 kHz TTS 译音进入同一 Worklet，逐采样 `clamp[-1, 1]`，输出真实峰值和限幅采样计数。
2. 应用侧虚拟输出接入：混音可发送到用户选定的既有 Render Endpoint；本地监听独立存在，默认只听译音，可选混合预听。
3. 应用侧真实验证：39/39 自动化测试通过；`verify:audio-routing`、`verify:overlay`、`verify:capture`、`verify:loopback` 全部通过。Windows 探针记录了真实混音和显式所选扬声器输出、增益比例、限幅、设备断开静音、系统回采隔离和 10 秒缓冲上限。
4. 设置融合：主窗、悬浮窗、设置页共享媒体宿主和严格路由配置；设置即时生效，`audio-settings.json` 原子保存，设备以 `deviceId` 和唯一完整 label 重绑定，缺失设备不回退。

这次原声/译音增益改变的是 DDTrans 的混音输出。它不会改变其他 Windows 应用的会话音量；Windows 原应用音量控制仍未接入。

## 尚未完成

- 当前机器没有虚拟设备，未完成 Teams、Discord、游戏或录音软件从配对 Capture Endpoint 收到混音的实机验证。
- 没有自有 `DDTrans Virtual Microphone`：正式 Windows 驱动、签名、安装卸载、升级、故障恢复和休眠恢复均未开始。
- 长会话下的断网、网络恢复、睡眠/唤醒、设备重插和长时间 TTS 队列稳定性尚未形成实机证据。
- 数据库的媒体保留、备份、导出、删除确认、孤儿媒体清理，以及更细的会话内说话人管理尚未完成。
- 热词仍需统一为明确的应用级/会话级配置来源。
- 多模型管理、本地视频翻译、协议扩展和实时变声尚未开始。

## 接下来优先顺序

### 1. 第三方虚拟设备外部软件实测

在安装 VB-CABLE、VoiceMeeter 或等价设备的 Windows 机器上，选择 Render Endpoint，并在至少一个会议软件、一个游戏语音或录音工具中选择配对 Capture Endpoint。验收：原声/译音增益、TTS 开关、默认译音监听和混合预听符合设置；暂停/恢复、目标语言切换和退出后设备句柄释放可复现；录音回放能证明外部应用实际收到的内容。

### 2. 完善声音控制与运行稳定性

先明确外放原声和混音原声的区别；若要在本应用中调低游戏/会议外放，增加明确选择目标应用的 Windows 音量控制。继续覆盖断网、重连、睡眠/唤醒、输出设备断开重插、长会话和缓冲压力。验收：不会重复发送旧音频，不会无限堆积，缺设备时保持关闭且明确提示，恢复后只在用户或唯一标签重绑定规则允许时重新打开。

### 3. 整理数据与配置归属

实现媒体保留/备份/删除策略、导出、孤儿媒体扫描、会话内说话人别名与筛选，以及热词的统一存储和回显合同。验收：删除、备份和恢复都可检查；同一设置不再分散在页面临时状态与多个存储位置。

### 4. 决定并实现自有 Windows 驱动

仅在第三方设备验证清楚端点和体验要求后，基于 Windows 虚拟音频驱动模型实现 `DDTrans Virtual Microphone`。验收：签名后的驱动可以安装、卸载、升级；设备可被外部应用枚举；应用与驱动以固定 PCM 格式和有界缓冲连接；休眠/唤醒、设备占用和异常退出都有明确行为。

### 5. 最后扩展产品能力

先以实测决定 WebSocket 之外是否需要 WebRTC/AOQ，再做多模型和本地视频的任务协议；实时变声另立音频链路，不与 TTS 音色或虚拟驱动混为一项。验收：新协议或模型复用现有会话收尾、段落归并和持久化合同；视频先完成单文件、时间轴和字幕导出后再做队列；变声有独立的延迟与路由验证。

具体的系统设备实现、第一期 Windows 11 x64 范围、签名与安装方案见 [DDTrans Virtual Microphone 制作方案](virtual-microphone-production-plan-2026-10-29.md)。
