# 音频路由四步实现与验证记录

日期：2026-10-29
范围：本轮完成真实混音、已有虚拟设备输出接入、应用侧验证和设置页融合。正式 `DDTrans Virtual Microphone` Windows 驱动不在本轮范围内。

## 结论

四个应用侧步骤已经落地：48 kHz 真实混音、把混音发送到用户选定的既有 Render Endpoint、应用侧链路验证、主窗/悬浮窗/设置页共享的路由设置。当前机器没有可用虚拟设备，因此不能把外部会议或游戏的 Capture Endpoint 收音写成已实测，也没有创建名为 `DDTrans Virtual Microphone` 的系统设备。

## 第一步：48 kHz 真实混音

系统声音或麦克风仍按原有流程以 16 kHz PCM 发送给模型；同一采集流同时进入 48 kHz、单声道混音总线。模型返回的 24 kHz TTS PCM 不再直接绑定普通扬声器，而是以译音流进入总线。

- 原声和译音各有实际生效的 `originalGain`、`translatedGain`。
- `ttsVolume` 是译音总量，作用于发送和监听；`monitorVolume` 只控制本地监听，二者分开保存和应用。
- 总线 Worklet 对每个采样相加后执行 `clamp[-1, 1]`，并上报原声、译音、混音真实峰值和限幅采样计数；混音处理只采用这一步逐采样限幅。
- TTS 播放队列最多缓存 10 秒；超过上限会拒绝新数据，不无限累积。

## 第二步：已有虚拟输出的应用侧接入

混音总线有两类独立输出：

- 本地监听：默认只听译音，可选“原声 + 译音”以预听发送效果。
- 独立虚拟输出：始终发送原声与译音的混音到用户选择的 Render Endpoint。

如果用户预先安装了 VB-CABLE、VoiceMeeter 等虚拟设备，可在设置页选择其播放端点，再在会议、游戏或录音软件中选择配对的 Capture Endpoint。应用按 `deviceId` 路由，并保存完整 label；设备 ID 变化时只在完整 label 唯一匹配时重绑定。设备缺失会关闭对应路由并报告错误，不会静默回退到默认扬声器。

Electron、Web Audio 与 Node.js 不能注册新的 Windows 麦克风设备。本轮没有伪造或创建 `DDTrans Virtual Microphone`；自有驱动、签名、安装、升级与恢复仍是后续工作。

## 第三步：已完成的应用侧验证

`data/probes/audio-routing-verification.json` 可读，记录了当前 Windows 环境的真实混音/回环数值：原声和译音同时存在、两路静音与比例调节生效、最大混音采样为 `1`、发生的限幅采样被计数、默认译音监听与监听音量比例生效，播放器缓冲受 `10000 ms` 上限约束。

该探针还确认：不存在的输出设备会得到“设备已断开，请重新选择或连接设备”，输出未就绪，没有回退到其他设备；快速关闭后设置可保存并在重开后恢复。`npm run verify:audio-routing` 与 `npm run verify:overlay` 已成功完成。

下表来自最终 `audio-routing-verification.json`，幅度是测试频率的观测值，不是主观响度或端到端延迟：

| 场景 | 原声 440 Hz 幅度 | 译音 997 Hz 幅度 |
| --- | ---: | ---: |
| 混音流，原声和译音均 100% | 0.11955 | 0.07936 |
| 混音流，原声 25% | 0.02995 | 0.08000 |
| 混音流，原声 0 | 0.00056 | 0.08000 |
| Windows 所选播放设备输出 | 0.24090 | 0.08530 |
| 同一路输出，本地监听量为 0 | 0.24108 | 0.08533 |
| 同一路输出，原声 0 | 0.00068 | 0.08601 |
| 不存在的输出设备 | 2.05e-6 | 2.20e-7 |

混音流和系统回环是不同测量点，因此不能跨行直接把幅度当作增益。小的非目标频率残余包含有限采样窗口的频谱泄漏。显式所选设备本轮为 `Speaker (Realtek(R) Audio)`，是普通扬声器；此项验证证明应用发送分支真实输出，未证明外部会议的虚拟 Capture Endpoint 已连通。混音最大采样为 `1`，限幅计数大于零；TTS 总音量从 100% 调至 25% 时，译音流幅度从 0.07997 降至 0.02000。播放器与待入队 PCM 均有 10 秒上限，停止后音频上下文及自有轨道已释放。

所选设备切换后，测试先留出 1200 ms 稳定时间再比较增益；该等待只是测量条件，不能被解读为实时输出延迟。

延迟字段只是已打开输出 `AudioContext` 的 `baseLatency + outputLatency` 估计；没有端到端延迟结论，也没有编造欠载计数。当前快照的 `underruns` 保持未知值，待将来真实设备桥接提供可观测数据后再实现。

## 第四步：设置页融合

`audio-routing-config` 是渲染进程和主进程共用的严格配置合同；无效字段或范围会被拒绝。Electron `userData/audio-settings.json` 使用临时文件后重命名的原子写入，运行中改动即时应用；设置页关闭、悬浮窗返回/退出或打开设置前，先完成待写入的音量刷新。

主窗、悬浮窗和设置页都通过同一个媒体宿主读取快照、发送路由命令和接收状态，不各自持有音频会话。异步的创建、换设备、停止和释放进入串行生命周期，避免并发操作交叉关闭上下文或残留设备句柄。

持久化的关键设置包括：

- 原声/译音增益、TTS 开关与 TTS 总音量；
- 本地监听开关、设备、内容和监听音量；
- 虚拟输出开关、Render Endpoint 和配对 Capture Endpoint；
- 固定格式：48 kHz、单声道。

## 代码入口

- `app/js/audio-routing-config.js`：共享设置默认值、标准化和严格校验。
- `app/js/audio-mix-bus.js`、`app/js/mix-worklet.js`：48 kHz 双输入混音、逐采样限幅、峰值/限幅计数、监听与独立输出。
- `app/js/audio-capture.js`：采集流同时服务模型输入与原声混音输入。
- `app/js/audio-engine.js`：24 kHz TTS 队列、总量控制、流输出和 10 秒上限。
- `app/js/media-session.js`、`app/js/media-host.js`：共享媒体宿主、运行中路由更新和串行生命周期。
- `app/js/settings.js`、`app/settings.html`：路由设置、设备状态和测试入口。
- `electron/audio-settings.js`：`audio-settings.json` 的读取、校验和原子写入。
